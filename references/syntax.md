# 統語の復元(比喩動詞・過剰名詞化・形式インフレ)

語彙や構造のクセより一段手前、文の骨格そのものが欠けているパターン。単語を禁止しても直らない。「誰が何をどうしたか」を書き直す作業になる。

`structures.md` の false agency を、技術文書・報告書向けに実務化したもの。元ネタは Zenn の記事「AIっぽい日本語」の分析と、そこで公開された yomiyasu(出典は CHANGELOG を参照)。Qiita 7万件の調査で、比喩的な「効く」「壊れる」「静かに」「黙って」が AI 以後に10倍から50倍に増えたと報告されている。

1. [非生物主語と身体性の比喩動詞](#1-非生物主語と身体性の比喩動詞) — 英語の直訳が日本語に居座る
2. [過剰名詞化](#2-過剰名詞化) — 主語・目的語・動作が名詞の連鎖に潰れる
3. [形式インフレ](#3-形式インフレ) — 太字と箇条書きで内容の薄さを補う
4. [復元の手順](#4-復元の手順)
5. [自分の文章を検査する](#5-自分の文章を検査する)

## 1. 非生物主語と身体性の比喩動詞

概念や事物が主語になり、人や体の動詞が当てられる。英語の "silently break" "works for" "land on" "silently ignored" を逐語訳した形で、因果が消える。読み手は「で、実際に何が起きたのか」を自分で補うことになる。

| 比喩動詞 | 出どころ | 例(AI版) |
|---|---|---|
| 静かに壊れる、静かに失敗する | silently break / fail | 順序性が静かに壊れる |
| 効く、効いてくる | works / pays off | 境界線が地味に効いてくる |
| 倒す | land on / lean toward | 柔軟性を共通側に倒す |
| 黙って無視される | silently ignored | リトライが黙って無視される |
| 溶かす | burn time | 調査に時間を溶かす |
| 走る | run | 重複処理が走る |

判定は動詞単体では決められない。「主語が無生物(概念、データ、設計、規則、処理)で、動詞が体の動作や感覚を借りているか」を見る。

**比喩ではないので残す例**:
- 「お握りを握って」「主導権を握る」(日常語と慣用句)
- 「過労で卒倒」「敵を倒す」(実際の動作)
- 「ブレーキが効く」「薬が効く」(物理的、薬理的に効果がある)
- 「静かに寝る」「黙って聞く」(人の振る舞いそのもの)

### 直し方

比喩動詞をその場で別の比喩に替えない。「壊れる」を「崩れる」に替えても同じ癖が残る。**物理的に何が起きたか**まで降りる。

| AI版 | 復元 |
|---|---|
| 順序性が静かに壊れる | 並列処理の完了順が入れ替わり、後から届いたメッセージが先に反映される |
| リトライが黙って無視される | 例外発生時のリトライが無効に設定されていて、エラーログにも何も出ない |
| 柔軟性を共通側に倒す | 共通部品に設定項目を足して、画面ごとの違いを吸収させる |
| 境界線が地味に効いてくる | モジュールの境界を決めておくと、変更の影響範囲が追いやすくなる |
| 調査に時間を溶かした | 原因の特定に3時間かかった |

「何が起きたか」が書けないなら、書き手がまだ把握していない。その文は保留して確認に戻る。

## 2. 過剰名詞化

「保守性担保機能の形骸化の防止」のように、名詞を「の」でつないで圧縮する。日本語の文が持つ要素が抜け落ちる。

| 要素 | 抜けるとどうなるか |
|---|---|
| 主語(誰が) | 行為者が分からない |
| 目的語(何を) | 対象が分からない |
| 動作 | 名詞化されて、手順が見えない |
| 条件 | いつ、どの場合に成り立つか分からない |

### 直し方

1. サ変名詞(〜化、〜の実施、〜の検討、〜の担保)を動詞に戻す。「実施の検討」は「検討して実施する」。
2. 「誰が」「何を」「どうする」「どの条件で」を一文に書き足す。
3. 名詞が4つ以上「の」「と」でつながっていたら、文を分ける。

| AI版 | 復元 |
|---|---|
| 保守性担保機能の形骸化の防止 | 保守性を確保するための機能が、使われないまま形だけ残らないようにする |
| メッセージ処理遅延の発生 | キューにメッセージが滞留し、処理が遅れた |
| 品質向上に向けた取り組みの推進 | レビューの回数を週1回に増やして、不具合の見落としを減らす |

役所の文書の癖でもあるので、人が書いても出る。ただし AI は意識せずに大量に出すため、まとめて点検する。

## 3. 形式インフレ

内容が薄いところを、太字、箇条書き、見出しの多さで補うパターン。AI が出力する文章は、強調と箇条書きの密度が高い。

- **太字を撒かない**。1段落に2か所以上あれば疑う。強調だらけだと、どこも強調されない。
- **箇条書きにしなくてよいものを箇条書きにしない**。因果や条件を含む説明は、地の文のほうが論理が追える。順序のある手順、並列の選択肢、項目間に関係のない列挙だけを箇条書きにする。
- **架空の否定対比を置かない**。「〜ではなく、〜である」で、読み手が持っていない誤解を先に否定している形。「これは単なるツールではなく、基盤である」。誤解を否定する前置きを削り、肯定文だけ残す。
- **短い決め台詞で段落を閉じない**。「順番が命だ。」「実例がすべてだ。」のように、文脈のない短文を最後に置く。

### 例外: 手順書とUI説明

手順書や画面の説明で、ボタン名やメニュー名を太字にするのは慣習で、形式インフレではない。「**送信**を押す」はそのまま残す。注意の囲みも、必ず守ってほしい警告に限って使う。

## 4. 復元の手順

どの文も同じ順で直す。

1. **行為者を特定する**。誰(何のプロセス)がやったか。
2. **物理的な出来事に還元する**。ログに何が出たか、画面で何が変わったか、数値がどう動いたか。
3. **主語、目的語、動作、条件を文に戻す**。名詞の連鎖をほどく。
4. **装飾を地の文に戻す**。太字、箇条書き、全角コロンの文末を整理する。

### 直すときの禁止事項

- 比喩動詞を別の比喩動詞に替えない。
- 短文を差し込んでリズムを作らない。`SKILL.md` の「ムラを入れる」を、短い決め台詞を足す理由にしない。ムラは、情報の密度が自然に違うところから出る。
- 意味を変えない。数値、固有名詞、コマンド、エラー文字列、パスは触らない。

## 5. 自分の文章を検査する

この skill の文章自体が比喩動詞を使っていると、説得力が消える。書いたあと、ripgrep で検査する。引用符の中の例示は除外して見る。

```bash
# 比喩動詞の候補(PCRE。日常の用法は先読み・後読みで外す)
rg -nP '(?<!お)(?<!権を)(?<!手を)握(る|り(?!飯))|(?<!卒)倒(す|し(?!れ))|静かに(壊|失敗|崩|劣化|進行)|黙って(無視|失敗|落ち|消え)|時間を溶か|(?<!薬が)(?<!ブレーキが)効(く|い(て|た))|処理が走' 対象.md

# 記号の症状
rg -n '：$|:$' 対象.md              # 文末のコロン
rg -nP '[ぁ-んァ-ヶ一-龠] [A-Za-z0-9]|[A-Za-z0-9] [ぁ-んァ-ヶ一-龠]' 対象.md  # 和欧間の半角スペース
rg -n '──|\*\*[^*]*$' 対象.md        # 全角ダッシュ、太字の残骸
```

ヒットは「候補」で、判断は人間がする。このリストは日常の用法を完全には除けないため、前節の「残す例」と照らして読む。

### 機械的な点数(目安)

自動検査を CI に載せるなら、減点方式が使いやすい。

| 項目 | 減点 |
|---|---|
| 比喩動詞 | 1件につき 10 |
| 記号違反(文末コロン、全角ダッシュ、和欧間スペース) | 1件につき 5 |
| 形式インフレ(段落内の太字2か所以上、不要な箇条書き) | 1件につき 5 |
| 名詞の過剰連続(4語以上) | 1件につき 3 |

100点から引いて、100点になるまで直す。**点数は修正の道具であり、文章の良し悪しの評価ではない**。
